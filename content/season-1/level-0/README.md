## 核心知识点

**Tool Calling**:模型提出「我想调用某个工具和参数」,由外部系统负责解析、校验、权限控制、分发、执行协调和结果反馈——模型自己不执行任何东西。

## 核心比喻:马、马具与马车

- **LLM = 一匹聪明、有力量的马**:有劲、认路(知识储备),但没有马具时,骑手的指令只能换来嘶鸣和原地打转。
- **Harness = 马具与挽具**:缰绳、嚼子、轭、车辕——负责连接、约束和传递力量,把「蛮力」变成「可控的拉力」。
- **Tool = 马车**:真正把拉力变成结果的部分——货物(任务)从 A 到 B,靠的是车,不是马直接驮。

故事线(正文展开):第一次给野马套马具的全过程——为什么先上嚼子(约束),再配轭(连接),最后才挂车(干活);核心冲突:力气大 ≠ 能干活,**可控的力气才等于能干活**。

## 概念映射表

| 比喻 | 技术 | 说明 |
|---|---|---|
| 马 | LLM | 提供决策与动力(生成工具调用意图) |
| 马具 / 挽具 | Harness | 解析、校验、权限控制、分发、执行协调、结果反馈 |
| 马车 | Tool | 完成具体动作(读文件、写文件、执行命令……) |
| 骑手指令 | 用户任务 | 整个链路的起点 |
| 货物送达 | 任务结果 | 验证「真的做到了」 |

## 真实的技术原理(TODO:正文时绘制 Mermaid 原理图;叙事插画单独制作)

一次 ToolCall 的旅程:

```text
用户任务 → LLM 生成结构化调用请求(JSON)
        → Harness:解析 → Schema 校验 → 权限检查
        → 分发到注册表中的 Tool → Tool 执行
        → 结果格式化 → 回填给 LLM → 组织最终回答
```

要点:Harness 是**工程概念**,不是某个特定的框架;任何「解析-校验-管控-分发」的系统层都可以叫 Harness。

## 比喻的局限

- 马具是被动的物理装置;真实 Harness 是主动运行的程序,每一步都在做判断。
- 马靠缰绳「感受」骑手;模型靠解析 JSON 文本理解请求,机制完全不同。
- 马车不会拒绝货物;真实 Tool 会失败、超时、越权,必须被 Harness 拦截。
- 马车是教学类比,不是严格的技术对应关系。

## 具体例子(正文展开)

`echo` 工具:任务「把这句话原样返回」→ 模型输出 `{"tool": "echo", "arguments": {...}}` → Harness 校验通过 → echo 执行 → 结果回填 → 模型确认完成。再演示一次失败:参数类型错误时请求被 Harness 当场拒绝,模型收到的是拒绝原因而不是执行结果。
